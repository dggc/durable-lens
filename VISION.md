# Vision

## The problem

[pi-durable](https://github.com/earendil-works/pi/tree/main/packages/durable) lets an agent harness survive crashes. It records everything the agent does in a store, so that a restarted process can continue where the last one stopped. The store is a SQLite file or a directory of JSONL files. It holds:

- the conversations: a root, forks of it, and subagents started by tasks;
- every entry in them: user input, assistant turns with their usage and timing, tool results;
- every task with its state: waiting, sleeping, pending after a crash, finished, with its input, checkpoint and outcome;
- documents, stored as a base and a chain of deltas, some of which can be rewound;
- the cost and tokens of every model call, kept in a usage document.

That is the complete history of what an agent did and why. It is also hard to see. Records are JSON inside SQL rows or JSONL lines. A document's value exists only after its deltas are replayed. A tool call, its task, its result and the conversation of the subagent it started are in four places. A harness that is running keeps the files open, so a tool that opens them can change them or show stale data.

durable-lens turns a store into something you can read: one timeline, a task graph, documents at any revision, and cost and time per turn.

## Who it is for

- Developers building on pi-durable who want to see what their harness did, for debugging a crashed or stuck task, or checking what a session cost.
- Teams that keep stores from production or CI runs and need to look inside one without running the code that wrote it.
- Authors of storage adapters, who can check that what their adapter wrote reads back as intended.

## Principles

1. **Never write to the user's store.** Not a byte of the database, its WAL or shared-memory file, or any JSONL file. This is stronger than opening read-only, which still writes beside a live SQLite database. Tests hash every file before and after a read.
2. **Work against a live owner.** A store may belong to a running process. Reading must take no locks, must not delay the owner's checkpoints, and must still show the latest committed state.
3. **Local only.** The viewer listens on loopback, serves under a random token, makes no network calls and sends no telemetry. The planned fork-and-rerun below is an explicit, opt-in command. It runs on a copy of the store and calls only the model provider that you configure. A future adapter for a remote store connects only to the store that you name.
4. **Store content is untrusted.** A transcript holds whatever a model or a tool produced. It is shown as text and is never executed or followed.
5. **Zero runtime dependencies.** The package installs nothing else. Every dependency would be code that reads your transcripts.
6. **Track every pi-durable release.** Each release from 1.2.0 on is covered by fixtures generated by that release itself, in a clean and a crashed state, and by tests over all of them. A store from a newer release shows what the reader understands, and shows the rest as JSON.

## Non-goals

- **Not a hosted service.** durable-lens runs on your machine, on your files. There is no account, no upload and no shared server.
- **Not an editor of the original store.** It does not repair, migrate, compact or modify the store it was pointed at, and it will not gain that ability.
- **Not affiliated with Earendil.** It reads pi-durable's storage formats and is tested against its releases. It is an independent project.

## Roadmap

These are plans. They may change, and none of them is a promise.

**0.1: the read-only viewer (now).** SQLite and JSONL stores from pi-durable 1.2.0, 1.3.0, 1.4.0 and the unreleased main. Timeline, task graph, documents with rewind, usage, fork comparison, a decoder hook for encrypted stores, JSON output, and a small library.

**Next (planned).** Fork any entry into a copy of the store and rerun it from there on another model, with the branches side by side. This always works on a copy. The original store stays untouched, as in every other feature. A rerun is a command that you start on purpose, and it contacts only the model provider that you configured.

**Later (planned).**

- Storage adapters beyond SQLite and JSONL, as listed under Limits in the [README](README.md): IndexedDB, Cloudflare Durable Object, Postgres and CouchDB.
- Keeping up with new pi-durable releases, each with its own fixtures.
- Larger stores. Today the whole store is read into memory. Incremental reads would make big sessions practical.
